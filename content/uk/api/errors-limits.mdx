<TLDR>
- Розрізняй помилки: **тимчасові** (429, 5xx, обрив мережі) повторюй з паузою, **помилки запиту** (400, 401, 404) — виправляй, повтор не допоможе.
- SDK сам робить 2 повтори для 408/409/429/5xx; лови помилки типізованими класами (`Anthropic.RateLimitError`…), а не за текстом.
- Навіть успішна відповідь (HTTP 200) може бути «невдалою»: завжди перевіряй <Term id="stop-reason" /> — `max_tokens`, `refusal`, `tool_use`.
</TLDR>

## Два типи помилок

| Код | Що сталося | Що робити |
| --- | --- | --- |
| 400 | неправильний запит (поле, формат, заборонений параметр) | виправити код, **не** повторювати |
| 401 | невірний чи відсутній ключ | перевірити `ANTHROPIC_API_KEY` |
| 404 | немає такої моделі чи ресурсу | перевірити назву моделі |
| 429 | перевищено <Term id="rate-limit" /> | зачекати й повторити |
| 500, 529 | проблема або перевантаження на боці API | повторити з паузою |

Правило: **4xx (крім 408/409/429) — твоя помилка, 5xx і 429 — тимчасові**.

## Ретраї правильно

<Term id="retry-backoff" /> — повтор зі зростаючою паузою: 1 с, 2 с, 4 с… Якщо API повернув заголовок `retry-after`, чекай стільки, скільки там сказано.

SDK уже робить 2 повтори для тимчасових помилок. Ти налаштовуєш кількість і ловиш те, що лишилось:

```ts
const client = new Anthropic({ maxRetries: 4 });

try {
  const res = await client.messages.create({ model: "claude-opus-5-5", max_tokens: 1024, messages });
} catch (error) {
  if (error instanceof Anthropic.RateLimitError) {
    queueForLater(messages); // ліміт не відпускає — відклади задачу
  } else if (error instanceof Anthropic.BadRequestError) {
    logBug(error.message); // помилка в запиті — повтор не допоможе
  } else if (error instanceof Anthropic.APIError) {
    console.error(error.status, error.message);
  } else {
    throw error;
  }
}
```

Перевіряй від конкретного класу до загального: усі вони успадковують `Anthropic.APIError` з полем `status`.

<Callout type="warn" title="Не ловити все одним catch">
`catch (e) { retry() }` повторює і 400 — і ти нескінченно платиш за той самий зламаний запит. Розгалужуй за типом помилки.
</Callout>

## stop_reason: HTTP 200 — ще не успіх

| stop_reason | Значення | Реакція |
| --- | --- | --- |
| `end_turn` | модель закінчила | використовувати відповідь |
| `max_tokens` | відповідь обрізано | збільшити ліміт / streaming |
| `tool_use` | модель хоче викликати інструмент | виконати й повернути результат |
| `refusal` | запит відхилено | показати користувачу зрозуміле повідомлення |

<Term id="refusal" /> приходить зі статусом 200, а деталі — у `stop_details` (категорія й пояснення). Якщо просто читати `content[0].text`, легко показати користувачу порожнечу як «успіх».

## Як не впертись у ліміти

- Обмеж **паралельність**: 10 запитів одночасно замість 200.
- Масові нетермінові задачі відправляй через <Term id="batch-api" /> — там окремі ліміти й половина ціни.
- Скорочуй вхід і кешуй незмінну частину промпту — менше токенів за хвилину.
