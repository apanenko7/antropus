<TLDR>
- Скажи, **як** має виглядати відповідь: <Term id="json" /> з такими ключами, таблиця, список, обсяг.
- Формулюй, що робити, а не чого не робити: «пиши суцільним текстом» замість «не використовуй списки».

## Опиши форму результату

Модель не знає, куди піде відповідь: у чат, у звіт чи в програму. Тому кажи прямо.

- **Для людини:** «таблиця: колонки Назва, Ціна, Мінус», «3 пункти по реченню», «до 100 слів».
- **Для програми:** «поверни лише JSON, без пояснень. Ключі: name, date (YYYY-MM-DD), items (масив рядків)».

## «Роби так», а не «не роби так»

Заборона вказує на проблему, але не на рішення. Модель краще слідує позитивним інструкціям.

<DoDont
  dont={["«Не використовуй markdown»", "«Не пиши довго»", "«Не будь занудним»"]}
  doThis={["«Пиши суцільними абзацами, без заголовків і списків»", "«До 80 слів»", "«Розмовний тон, як у повідомленні колезі»"]}
/>

<Callout type="tip" title="Стиль промпту = стиль відповіді">
Якщо твій промпт рясніє markdown-списками, відповідь теж буде зі списками. Хочеш прозу — пиши промпт прозою.
</Callout>

## Роль і system prompt

Роль задає перспективу: «Ти — юрист, що перевіряє договори для малого бізнесу». Це працює, але **роль не замінює контекст**. Важливіше, що саме перевіряти й для кого.

У Claude.ai роль і постійні правила зручно класти в інструкції проєкту, в API — у поле system, у Claude Code — частково в <Term id="claude-md" />.

## Structured outputs: коли відповідь читає код

Якщо результат одразу йде у твій застосунок, в API можна передати JSON-схему, і відповідь **гарантовано** їй відповідатиме. Жодних «Ось ваш JSON:» чи зайвих ком, через які падає парсинг.
