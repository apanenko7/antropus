## Навіщо spec, якщо агент і так розумний

Агент чудово читає код, але не бачить твоєї голови: для кого фіча, що важливо, а що ні. Без специфікації він заповнює прогалини здогадками, і ти переробляєш.

Spec-driven development: **спершу документ «що і навіщо», потім код**. Цей самий документ потім стає мірилом для рев'ю.

## Що має бути в специфікації

| Розділ | Навіщо |
| --- | --- |
| Ціль | Одне-два речення: яку проблему вирішуємо |
| Поза рамками (non-goals) | Що НЕ робимо — інакше агент «допоможе» зайвим |
| User stories | Хто користувач і яка йому користь |
| Критерії приймання | Перевірювані умови «готово» |
| Обмеження | Технології, продуктивність, сумісність, безпека |
| Відкриті питання | Що ще не вирішено — щоб не вирішилось випадково |

### Given / When / Then

Найкорисніший формат критеріїв, бо з кожного рядка виходить тест:

```
Given користувач перевищив 100 запитів за хвилину
When він робить ще один запит
Then API відповідає 429 і заголовком Retry-After
```

## Хай агент тебе проінтерв'ює

Коли ще не все продумав, не мучся над документом сам. Попроси Claude ставити питання, доки не набереться spec:

## Від spec до плану

1. Нова сесія → <Term id="plan-mode" /> (Shift+Tab).
2. «Прочитай SPEC.md і запропонуй план реалізації».
3. Ти правиш план, поки він тебе влаштовує, і лише тоді агент пише код.
